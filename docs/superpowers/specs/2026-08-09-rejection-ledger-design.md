# 후보 파이프라인 (기각 원장) — 설계 명세

> **작성일**: 2026-08-09
> **대상 파일**: `index_kelly.html` (TOOL 04), `PRD.md`
> **상태**: 설계 확정, 구현 전

---

## 1. 배경 — 왜 만드는가

펀치카드 프레임(20칸 평생 한도)을 이 파이프라인에 대입하면 세 가지 공백이 드러난다.

**① 이미 뚫린 칸이 계상되지 않는다.** 인적자본(반도체 커리어 + 성과급)은 되돌릴 수 없는 1칸인데 어떤 도구에도 없다. 신규 후보 평가의 첫 질문은 "좋은 회사인가"가 아니라 "이미 뚫린 칸과 다른 칸인가"여야 하는데, 현재 파이프라인(Circle → Premium → RIM → Kelly)에는 그 필터가 없다.

**② 연구 대기열이 펀치 예산보다 길다.** 대기열 5~6건이 상시 존재한다. 여기 깔린 무의식적 전제 — *"공부한 회사는 결국 산다"* — 가 검증되지 않는다. 공부의 정상적 결과 분포는 10건 중 8~9건 기각이어야 하는데, 기각률을 측정할 데이터가 없다.

**③ 기각 판단이 반증 불가능하다.** TOOL 04의 재평가 원장은 **보유 종목만** 추적한다. 기각한 후보의 판단 근거는 어디에도 남지 않는다. 그래서 "fair PBR 4~5배로 보고 10배대에서 손을 뗐는데 3년 뒤 주가가 그 위에 있다" 같은 사건이 발생해도, RIM 모델의 `r=10%` 가정이나 moat duration 추정으로 피드백이 돌아가지 못한다.

**펀치카드의 가치는 뚫은 칸이 아니라 안 뚫은 칸에 있다.** 이 기능은 안 뚫은 칸을 기록 가능·검증 가능하게 만든다.

**안 한다**

- 팩터 노출 대시보드 · 팩터 태그 체계 · 자동 중복 판정 — 팩터 중복은 **기각 사유 코드 하나**로만 존재한다
- 칸 카운터 UI (예: "20칸 중 4칸 사용") — 근거는 §9
- 도구 간 데이터 연동 (P2 키 공유 금지 유지)
- 알림·리마인더 (로컬 도구, 배지 표시로 대체)

## 3. 데이터 모델

`kelly2y`에 두 개를 추가한다.

```js
candidates: [
  {
    id: 'lz8k3m',              // Date.now().toString(36) — holdings와 동일 방식
    name: '코스트코',
    status: 'reviewing',       // 'reviewing' | 'rejected'
    startDate: '2026-06-01',   // 검토 시작일 = 등록 시각 자동 기록 (§6.1, 입력받지 않음)

    // status === 'rejected' 일 때만 채워짐
    rejectedDate: '2026-08-09',  // 사용자가 입력하는 기각일 (소급 가능)
    rejectedAt: 1786000000000,   // 기각 등재를 누른 실제 시각 (ms) — 유예·소급 판정용
    rejectPrice: 142,          // 기각 당시 주가 (USD)
    rejectReason: 'factor',    // §4의 6종
    trigger: 'PBR 6배 이하로 오면 재검토',   // 자유 텍스트, 필수
    note: '',                  // 선택
    linkedHoldingId: null,     // thesis 자동 등재 시 원 종목 id

    verify: null               // 3년 검증 전까지 null
    // verify: { date:'2029-05-02', price:310, verdict:'wrong', note:'...' }
  }
],
rejIntroDate: 1786000000000    // 이 기능 도입 시각 (ms) — 기각률 분모 필터용, 1회만 기록
```

**편입은 `candidates`에 남기지 않는다.** 검토중 후보를 편입하면 `candidates`에서 삭제하고 기존 `holdings`에 추가한다. 편입 건수는 `holdings`에서 세므로 같은 사실이 두 곳에 저장되지 않는다.

**통화**: `rejectPrice`·`verify.price`는 USD 고정. `load()`가 이미 `h.ccy='USD'; h.fx=1`로 강제하고 있어(`index_kelly.html:1322`) 도구 전체가 달러 계좌 전제다. 후보에 통화 필드를 두지 않는다.

### 3.1 `holdings[]`에 `status:'rejected'`를 넣지 않는 이유

`holdings`는 `price`·`up`·`down`·`prob`가 필수다(`index_kelly.html:522`). 그런데 Circle 단계나 팩터 중복으로 기각한 후보는 그 숫자를 애초에 계산한 적이 없다.

- 억지로 채우면 거짓 데이터가 된다
- 비워두면 `kellyOf()`·정규화·40% 캡 로직에 `null`이 흘러든다

별도 배열이 안전하다.

## 5. 화면

`목표 포트폴리오` 카드 아래에 새 `<h2>` 카드를 둔다. 현재 파일은 탭이 아니라 세로 스크롤 카드 구조(`투자 원금` → `종목 추가` → `목표 포트폴리오`)이므로 그 패턴을 따른다.

```
── 후보 파이프라인 ─────────────────────────
 검토중 3 · 기각 11 · 편입 3 · 칸 회수 1
 기각률 11/14 = 79%

                [+ 후보 등록]

 ▸ 검토중                          (오래된 순)
   ┌────────────────────────────────┐
   │ Costco          69일 · 2026-06-01│
   │          [기각] [편입] [삭제]     │
   └────────────────────────────────┘
   Progressive      35일 · 2026-07-05
   Visa             20일 · 2026-07-20

 ▸ 기각                            (최신 순)
   ┌────────────────────────────────┐
   │ Arista              2026-08-09  │
   │ $142 · 팩터 중복                 │
   │ ↻ 반도체 노출 줄면 재검토          │
   │ ⏳ 검증 D-1095            [✎]    │
   └────────────────────────────────┘
   ┌────────────────────────────────┐
   │ TSMC                2023-05-02  │
   │ $210 · 밸류에이션      [소급 등록] │
   │ ↻ PBR 6배 이하 재검토             │
   │ 🔍 검증 필요             [검증]   │
   └────────────────────────────────┘

 ▸ 칸 회수                          (최신 순)
   ┌────────────────────────────────┐
   │ Nvidia              2026-03-11  │
   │ $890 · thesis 파기 청산          │
   │ ↻ 데이터센터 성장 재가속 시 재검토  │
   │ ⏳ 검증 D-944             [✎]    │
   └────────────────────────────────┘
```

**기각과 칸 회수는 별도 섹션이다.** 헤더가 `기각`(thesis 제외)과 `칸 회수`(thesis만)를 따로 세므로, 목록도 같은 기준으로 나뉘어야 헤더 숫자와 목록 길이가 1:1로 대응한다. 한 목록에 섞으면 "기각 2"인데 카드가 3장 보이는 상태가 되고, 자기 회계의 정확성이 존재 이유인 도구에서 그 불일치는 신뢰를 직접 깎는다. 두 섹션은 동일한 카드 마크업을 쓰므로 렌더는 공유 헬퍼 `rejectCard(c, now)` 하나로 처리한다.

*위 화면은 도입 후 몇 달이 지난 상태다. 도입 직후에는 §6.1대로 대기열 전부가 `0일`로 시작한다.*

**정렬**: 검토중은 **오래된 순**(시작일 오름차순). 흐지부지 항목이 화면 위쪽을 차지해 압력을 유지하는 것이 이 목록의 목적이다. 기각은 최신 순.

**헤더에 넣지 않는 것**: "검토중 3건 = 향후 4.5년치 칸" 같은 환산 경고. 근거는 §9.

## 6. 동작 명세

### 6.1 후보 등록
- 입력: **종목명뿐이다.** 검토 시작일은 등록 시각으로 자동 기록하며 입력받지 않는다.
- `status: 'reviewing'`으로 저장

**기존 대기열(Costco · Visa/Mastercard · Danaher/Thermo Fisher · Progressive · Arista)도 전부 도입일에 새로 등재된 것으로 처리한다.** 과거 시작일을 지금 기억으로 적는 것은 §6.5가 문제 삼은 소급 등록과 같은 성질이다 — "언제부터 봤더라"는 부정확하고, 진척 상황을 아는 상태에서 유리하게 적을 여지가 있다. 흐지부지 압력은 **도입일 이후 쌓이는 일수**로 충분히 달성되므로 과거 일수는 필요 없다.

기각일(`rejectedDate`)의 소급 입력은 별개로 허용한다. 근거는 §6.5.

### 6.2 기각
- 검토중 항목의 `[기각]` 또는 `[+ 후보 등록]`에서 바로 기각으로 등록
- 입력: 기각일(기본 오늘, 과거 허용) · 당시 주가(필수) · 사유 6종 중 1개(필수) · 재검토 트리거(필수, 자유 텍스트) · 메모(선택)
- 트리거를 필수로 두는 이유: *"PBR 6배 이하로 오면 재검토"* 처럼 **구체적 숫자**가 있어야 3년 뒤 검증이 판정 가능해진다. 트리거 없는 기각은 검증할 대상이 없다.
- `status: 'rejected'`로 전환

### 6.3 편입
- 검토중 항목의 `[편입]` → 기존 `종목 추가` 폼에 종목명을 프리필한 상태로 이동
- **후보 삭제 시점은 `holdings`에 항목이 실제로 생성된 직후다.** 폼으로 이동하는 시점에 지우면 사용자가 입력을 중단했을 때 후보가 소실된다.
- 후보 등록 없이 바로 `종목 추가`를 써도 무방하다. 편입 카운트는 `holdings`에서 세므로 누락되지 않는다.

### 6.4 삭제 · 수정 (14일 유예)

```js
const GRACE_MS = 14*864e5;
const editable = Date.now() - c.rejectedAt < GRACE_MS;
```

**기준 시각은 `id`(후보 등록 시각)가 아니라 `rejectedAt`(기각 등재 시각)이다.** `id`를 쓰면 70일 전에 후보로 등록한 종목을 오늘 기각하는 순간 이미 유예기간이 지나 있어 즉시 수정 불가가 된다. `rejectedDate`도 쓸 수 없다 — 사용자가 소급 입력할 수 있는 값이라 유예기간을 임의로 늘릴 수 있다.

| 대상 | 정책 |
|---|---|
| 검토중 항목 | 언제나 자유 삭제 — 아직 결론이 아님 |
| 기각 항목, 등재 후 14일 이내 | 삭제·전체 수정 자유 |
| 기각 항목, 14일 경과 후 | 삭제 불가. **재검토 트리거와 메모만** 수정 가능 |

근거: 오타는 등록 직후 발견되고, 합리화("이건 기각이 아니라 그냥 안 본 걸로 하자")는 몇 년 뒤 일어난다. 시간이 두 실패 모드를 가른다.

14일 경과 후에도 `dataSnapshot` export → JSON 편집 → import 경로는 열려 있다. 즉 이 잠금의 실질은 물리적 차단이 아니라 **UI 마찰**이다. 그것으로 충분하다.

> **주의**: 기존 원장(`ledger`)은 이런 제약이 없다. `index_kelly.html:1144, 1153, 1169`에서 모든 항목에 ✕ 버튼이 조건 없이 렌더되고 `1272-1276` 핸들러는 확인창도 없이 삭제한다. PRD §4.4의 *"과거 기록은 값 수정(✎)만 허용, 삭제 후 재입력 불가"* 는 코드와 어긋난 드리프트다(§8에 기록). 따라서 이 유예 규칙은 **기존 정책과의 일관성이 아니라 이 원장에 특별히 필요한 증거력을 근거로** 도입된다.

### 6.5 소급 등록 배지

기각 원장의 증거력은 "그때 기록했다"는 데서 나온다. 지금 기억으로 적은 기각은 당시 근거를 현재 결과에 맞춰 각색할 여지가 있어 반증 강도가 다르다.

**자동 판정한다.** `rejectedAt`에 실제 등재 시각이, `rejectedDate`에 사용자가 주장하는 기각일이 들어 있다.

```js
const seeded = c.rejectedAt - Date.parse(c.rejectedDate) > GRACE_MS;
```

14일 이상 차이 나면 `[소급 등록]` 배지를 단다. §6.4의 유예기간과 같은 상수를 재사용한다.

### 6.6 3년 검증

- `rejectedDate + 1095일`이 검증 기준일
- 배지: 기준일 전 `⏳ 검증 D-{n}` / 기준일 도달 `🔍 검증 필요`(강조색) / 완료 후 `✓ 검증 완료`
- 36개월은 고정 상수다. 사용자 지정 입력을 두지 않는다 (P6 — 실사용에서 답답하면 상수 한 줄 변경)
- 검증 모달 입력: 현재가(필수) · 판정 3택(`right` 옳았다 / `wrong` 틀렸다 / `unclear` 판단보류) · 메모
- 완료 시 카드에 변화율 표시: `$210 → $310 (+48%) · 기각이 틀렸음`
- 모달 하단 고정 문구:

  > 기각이 틀렸다면 TOOL 03의 `r`·`N` 가정을 재검토하세요.

  이 문구가 기능의 핵심이다. 기각 판단이 반증되면 RIM 모델의 요구수익률·moat duration 추정으로 피드백이 돌아가야 한다. 이 연결이 없으면 원장은 기록일 뿐 학습 장치가 아니다.

### 6.7 thesis 파기 자동 등재

전량 청산(`netShares`가 0이 되는 매도) + `thesisBroken`이면 기각 등재 모달을 띄운다.

`thesisBroken` 판정은 기존 로직을 그대로 쓴다 (`index_kelly.html:1536`):

```js
const thesisBroken = (reason==='thesis'||reason==='criteria'||reason==='better');
```

`target`(상단 목표가 도달)·`rebal`(리밸런싱)은 **칸 회수가 아니므로 제외**된다. 밸류에이션 기반 청산은 thesis가 유지 중이라 칸을 계속 쓰고 있는 상태다.

모달 내용:

```
┌ 칸 회수 ────────────────────┐
│ thesis 파기로 청산했습니다.    │
│ 기각 원장에 등재됩니다.        │
│ 재검토 트리거? [__________]   │
│                    [등재]    │
└─────────────────────────────┘
```

등재되는 레코드: `rejectReason:'thesis'`, `rejectPrice`=매도 체결가, `rejectedDate`=매도일, `linkedHoldingId`=원 종목 id.

### 6.8 재진입 경고

`종목 추가` 시 같은 이름의 `rejectReason:'thesis'` 기각 이력이 있으면 경고 배너를 띄운다.

```
┌─────────────────────────────┐
│ ⚠ 과거 thesis 파기 종목       │
│ 새 1칸을 씁니다.              │
│ 기존 기록에 이어 붙일 수 없습니다 │
│ — 새 항목으로 추가됩니다.       │
└─────────────────────────────┘
```

기존 `holdings` 행에 이어 붙이지 않고 **새 `holdings` 항목으로 강제**한다. 이것이 교훈 4의 핵심 규율이다 — *"예전에 봤던 회사니까"는 칸을 아껴주지 않는다. 오히려 한 번 틀렸던 회사이므로 검증 기준이 더 높아야 한다.*

이름 매칭은 공백 제거 + 대소문자 무시로 한다. 완벽한 동일성 판정은 불가능하므로 **경고이지 차단이 아니다** — 사용자가 진행을 선택할 수 있다. 다만 진행 시 항상 새 항목이 된다.

**우회 경로 차단**: thesis 청산 후에도 원 `holdings` 항목은 historical 행으로 남아 있고(`index_kelly.html:1012`), 그 행의 기록 모달에서 새 `buy` 항목을 추가할 수 있다. 이 경로로 들어가면 위 경고가 발동하지 않아 규율이 무력화된다.

따라서 `linkedHoldingId`로 연결된 thesis 기각이 존재하는 `holdings` 항목에는 **새 `buy` 기록을 막는다.** 기존 기록의 수정(✎)과 열람은 그대로 허용한다.

```
이 종목은 thesis 파기로 청산했습니다.
재진입은 새 1칸입니다 — [종목 추가]로 새로 등록하세요.
```

## 7. 기각률 계산

```js
const introMs = rejIntroDate;
const realRejects  = candidates.filter(c => c.status==='rejected' && c.rejectReason!=='thesis');
const punchesBack  = candidates.filter(c => c.status==='rejected' && c.rejectReason==='thesis');
const adopted      = holdings.filter(h => {
  const t = parseInt(h.id, 36);
  return Number.isFinite(t) && t >= introMs;
});

const denom = realRejects.length + adopted.length;
const rate  = denom ? realRejects.length / denom : null;
```

**`thesis`를 분자에서 제외하는 이유**: thesis 파기 청산은 "샀다가 판 것"이다. 분자(기각)와 분모의 편입 항목에 같은 종목이 동시에 들어가 비율이 부풀려진다. 기각률의 의미는 "검토한 것 중 몇 %를 안 샀나"이므로 산 적 있는 종목은 빠져야 한다.

`thesis` 건은 별도로 **"칸 회수 N건"** 으로 표시한다. 교훈 4의 회수 규율이 실제로 작동하는지 보는 독립 지표다.

**분모의 도입일 필터**: `holdings.length`를 그대로 쓰면 도구 도입 이전에 산 종목이 전부 분모에 들어가고 기각은 오늘부터 쌓이므로 초기 몇 년간 비율이 왜곡된다. `id`가 `Date.now().toString(36)`이므로(`index_kelly.html:869`) 생성 시각을 역산할 수 있다. 역산 실패하는 레거시 id는 도입 이전으로 간주해 분모에서 제외한다.

**분모가 0일 때**: 비율을 표시하지 않고 카운트만 표시한다.

## 9. 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| 팩터 노출 대시보드 + 자동 중복 판정 | 팩터 태그 체계·저장소·포트폴리오 연동을 새로 설계해야 하고 코드량 3~4배. 팩터 중복 판단은 결국 사람이 한다. 사유 코드 하나로 충분 (P6) |
| 별도 도구(`index_reject.html`) | 기각률 분모(편입 건수)가 `kelly2y`에 있는데 P2(키 공유 금지)로 접근할 수 없다. 백업 체계도 따로 만들어야 한다 |
| 허브(`index.html`)에 배치 | 위와 동일. 추가로 정적 진입점을 상태 보유 화면으로 바꾸게 된다 |
| `holdings[]`에 `status:'rejected'` 추가 | §3.1 참조. 필수 숫자 필드가 없는 후보가 켈리 계산 로직에 흘러든다 |
| 칸 카운터 UI ("20칸 중 4칸") | 원 프레임 스스로 *"자금이 계속 유입되므로 20칸이 안 맞는다"* 고 인정한다. 20이라는 숫자를 UI에 박으면 **이미 기각된 전제를 코드에 고정**하게 된다. 추적할 것은 칸 개수(count)가 아니라 칸의 중복도(overlap)다 |
| "검토중 N건 = 향후 M년치 칸" 환산 경고 | 위와 같음. `1.5년/칸`은 `30년 ÷ 20칸`에서 나온 숫자다 |
| 기각 항목 완전 삭제 불가 | 도구 전체에서 유일하게 못 지우는 기록이 되는데, 그 일관성 근거(PRD §4.4)가 코드와 어긋난 드리프트였다. 오타가 영구히 남는 비용이 편향 차단 이득보다 크다 |
| 검토 시작일 소급 입력 | 기억 기반 날짜는 부정확하고, 진척 상황을 아는 상태에서 유리하게 적을 여지가 있다 — §6.5가 기각에서 문제 삼은 것과 같은 성질이다. 흐지부지 압력은 도입일 이후 쌓이는 일수로 달성되므로 과거 일수가 없어도 목적을 잃지 않는다 (§6.1) |
| 3년 검증 시점 사용자 지정 | P6. 답답하면 상수 한 줄 변경 |
| 검증 리마인더 알림 | 서버·푸시 없는 로컬 도구. 배지로 대체 |

## 10. 검증 방법 (P5)

수식이 없는 기능이지만 계산 로직 세 개는 Node.js DOM-stub로 단위 검증한다.

| 대상 | 검증 케이스 |
|---|---|
| 기각률 | ① `thesis` 건이 분자·분모 어디에도 안 들어감 ② 도입 이전 `holdings`가 분모에서 제외됨 ③ `parseInt(id,36)`이 `NaN`인 레거시 id 제외 ④ 분모 0일 때 `null` 반환 |
| 14일 유예 | ① `rejectedAt` 13일 23시간 전 → 삭제 가능 / 14일 1분 전 → 불가 ② **후보를 70일 전 등록하고 방금 기각 → 유예가 살아 있어야 함** (`id` 기준이면 실패하는 케이스) ③ `rejectedDate`를 1년 전으로 소급 입력해도 유예가 늘어나지 않음 |
| 소급 판정 | `rejectedAt == rejectedDate` → 배지 없음 / `rejectedDate`가 15일 전 → 배지 있음 |
| 검증 D-day | `rejectedDate + 1095일` 경계 전후 |

수동 확인:
- 기존 `kelly2y` 데이터를 브라우저에 넣고 파일을 열어 **데이터 손실 없음** + `rejIntroDate`가 1회만 기록되는 것 확인
- 검토중 후보 `[편입]` → 종목 추가 폼에서 **취소** → 후보가 그대로 남아 있는지 (§6.3)
- thesis 청산된 historical 행에서 새 매수 기록 시도 → 차단 메시지 (§6.8 우회 경로)

## 11. PRD 갱신 항목

| 위치 | 내용 |
|---|---|
| §2 | **P8. 칸 회계** — 신규 편입 전 "이미 뚫린 칸과 다른 칸인가"를 먼저 묻는다. 인적자본(반도체 커리어)은 되돌릴 수 없는 1칸으로 계상한다. 기각 판단은 기록되어야 반증 가능하다 |

### D15 — '1칸' 소모 정의표

| 행위 | 칸 소모 |
|---|---|
| 새 기업 최초 편입 | **1칸** |
| 8분기 분할 매수 (같은 종목) | 0칸 — 1칸 안의 절차 |
| 밸류에이션 기반 분할 매도 후 재매수 | 0칸 — thesis 유지 중 |
| **thesis 파기 후 청산 → 나중에 재진입** | **새 1칸** |
| 매크로 ETF 바스켓 (예: 구리 4종) | 테마당 1칸, 종목당 아님 |

칸이 뚫리는 순간은 1차 매수 시점이 아니라 **thesis를 확정한 순간**이다. 따라서 분할매수 도중 tranche를 건너뛰는 것은 **칸을 회수하는 행위**다. 원본 펀치카드는 되돌릴 수 없지만 이 시스템은 8분기 동안 되돌릴 수 있다 — 회수를 한 번도 하지 않으면 그 우위가 소멸한다.

## 12. 이 기능의 기각 조건

3년 후 기각 원장을 열었을 때 **기각 건이 0이면**, 이 도구는 규율이 아니라 사후 서사로 쓰이고 있는 것이다. 그 경우 기능을 유지할 이유가 없다.

측정 가능한 형태로 다시 쓰면 — 도입 3년 시점에 다음 중 하나라도 해당하면 재검토한다:

- `realRejects.length === 0`
- 기각률 < 50% (프레임워크가 필터가 아니라 정당화 장치로 작동)
- 검토중 항목이 전부 결론 없이 1년 이상 방치 (등록 습관이 안 붙음)
- 3년 검증 완료 건 0 (피드백 루프 미작동)
