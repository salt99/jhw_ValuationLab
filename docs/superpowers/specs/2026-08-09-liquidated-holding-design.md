# 설계 — 논지 훼손 청산 종목을 계획에서 제외

**날짜**: 2026-08-09 · **대상**: `index_kelly.html` (TOOL 04) · **상태**: 승인됨, 미구현

## 1. 관측된 증상

실사용 중 발견. 논지 훼손으로 전량 매도한 종목이 분기 매매일지에 계속 남았다.

스크린샷(`2026-08-09`) 기준, 청산된 카드가 이렇게 렌더됐다:

```
sjhss                     순매수 $-36 / 목표 $14,332 (-0%)
2026Q2 시작 · 현재가 $266 · 하단 ▼$255 · 매도 1회
▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓          ← 진행 바가 꽉 참
매수 1회 · 보유 0주 · 이번 분기 목표 $2,053 · 7분기 남음
```

보유 0주인데 목표 $14,332과 분기 목표 $2,053을 제시한다.

## 2. 근본 원인

### 2-A. 계획이 원장을 안 본다 (주 원인)

`compute()` — `index_kelly.html:841-842`

```js
const rows=holdings.map(h=>({h,k:kellyOf(h)}));
const pos=rows.filter(r=>r.k.f&&r.k.f>0);
```

`kellyOf(h)`는 `price·up·down·prob`만 쓴다. 원장을 참조하지 않으므로 **전량 매도해도 켈리 값이 변하지 않는다.** 상단·하단·승률을 수정하지 않은 채 청산하면 켈리가 양수로 남아 `pos`에 계속 포함된다.

일지 렌더의 비활성 판정도 같은 한계를 물려받는다 — `index_kelly.html:1241`

```js
const isInactive = r.inactive || kNow.f===null || kNow.f<=0;
```

`r.inactive`는 `pos`에 **없는** 행에만 붙으므로(`1202-1203`), 켈리가 양수인 청산 종목은 끝까지 활성으로 렌더된다.

**앱은 이미 스스로 모순된다.** `openLogModal`은 같은 종목의 신규 기록을 막는다 — `index_kelly.html:1916`

```js
if(thesisRejectOf(h.id)){
  setStatus('thesis 파기로 청산한 종목입니다 — 재진입은 [종목 추가]로 새로 등록하세요',true);
  return;
}
```

계획은 "이번 분기에 $2,053 사라"고 하고, 누르면 "청산한 종목입니다"라고 막는다. `compute()`도 일지 렌더도 `thesisRejectOf()`를 한 번도 참조하지 않는다.

### 2-B. 배분 희석 (파생, 숫자가 틀림)

`index_kelly.html:843-845`

```js
const posSum=pos.reduce((s,r)=>s+r.k.f,0);
pos.forEach(r=>r.rel=posSum>0?r.k.f/posSum:0);
```

청산된 칸이 `posSum`에 들어가 살아있는 종목의 목표 비중을 갉아먹는다. 표시만의 문제가 아니라 **실제 배분 숫자가 틀리다.**

### 2-C. 진행 바 음수 (독립 버그)

`index_kelly.html:1214`

```js
const investedPct = targetAmt>0 ? Math.min(100, st.netInvested/targetAmt*100) : 0;
```

`Math.min`은 위쪽만 자른다. 순매수가 음수면(전량 매도 후 매도액 > 매수액) `investedPct`도 음수가 되고, `1305`행의 `style="width:${investedPct}%"`가 `width:-0.25%`라는 **유효하지 않은 CSS**를 만든다. 브라우저가 이 선언을 버리면 `.exec-track-fill`에는 기본 `width`가 없으므로(`136-137`) 블록 요소 기본값 `auto` = 부모 100%로 렌더된다. 그래서 "목표 달성"처럼 보인다.

### 2-D. 칸 회수 등재를 빠져나갈 수 있다

`index_kelly.html:1816-1817`

```js
$('rj-close').addEventListener('click', ()=>{ $('rjModal').style.display='none'; });
$('rjModal').addEventListener('click',e=>{if(e.target===$('rjModal'))$('rjModal').style.display='none';});
```

전량 매도는 이미 저장된 뒤(`2159`) 모달이 열리므로(`2166-2173`), 모달을 닫으면 **매도는 기록되고 칸 회수는 등재되지 않은 상태**가 된다. PRD §4(147행)는 "칸 회수 **강제**"라고 규정하는데 코드가 지키지 않는다.

이 상태는 지금은 무해하지만, 청산 종목을 포트에서 빼는 이번 변경과 합쳐지면 **어디서도 도달할 수 없는 종목**을 만든다.

## 3. 결정

논지 훼손으로 전량 청산한 종목은 **목표 배분과 분기 매매일지 양쪽에서 사라진다.** 회고용 매매 이력은 `holdings`에 그대로 남기고, 후보 파이프라인의 `▸ 칸 회수` 카드에서 열람한다.

**기각한 대안**

| 대안 | 기각 이유 |
|---|---|
| 일지에는 `▸ 청산` 섹션으로 남긴다 | 사용자가 "두 곳 다에서 사라지는 게 깔끔하다"고 판단 |
| `holdings`에서 실제로 삭제한다 | 회고용 원장이 사라진다. `candidates` 스키마에는 원장을 담을 자리가 없다 |
| 8분기 트랜치 UI를 칸 회수 카드에서 재사용 | 106KB 단일 파일에서 마크업 덩어리를 추출하는 회귀 위험. 청산된 포지션에 "이번 분기 열림"은 의미가 없다 |

## 4. 설계

### 4-1. 청산 판정

기존 함수를 그대로 쓴다 — `thesisRejectOf(h.id)` (`1666-1669`). 새 개념을 만들지 않는다.

### 4-2. 제외는 `compute()` 한 곳에서

```js
function compute(){
  const live=holdings.filter(h=>!thesisRejectOf(h.id));   // 청산 = 계획에서 제외
  const rows=live.map(h=>({h,k:kellyOf(h)}));
  ...
```

`rows`에서 빠지면 `pos`·`posSum`·`historical` 버킷(`1202`)이 전부 따라 빠진다. 목표 배분·매매일지·배분 정규화가 한 번에 해결된다. `holdings` 배열과 원장은 건드리지 않는다.

**소비처 확인** — `compute()` 호출은 두 곳뿐이고 둘 다 안전하다:

- `1130` 렌더 — 의도한 동작
- `1981` `tgtAmtFor(h)` — `pos`에 없으면 `0`을 반환. 청산 종목은 `openLogModal`이 이미 막으므로 도달하지 않는다

### 4-3. 회고 이력 — 칸 회수 카드

`▸ 칸 회수` 카드에 `[매매 이력]` 버튼을 달고, 읽기 전용 모달을 연다.

```
┌─────────────────────────────────┐
│ sjhss · 매매 이력                │
│ 매수 1회 $630 · 매도 1회 $666    │
│ ─────────────────────────────── │
│ 2026Q2                          │
│  매수 2026-08-09 @$210 · 3주    │
│   "jshsh"                       │
│  매도 2026-08-09 @$222 · 3주    │
│   원 논지 훼손 · "..."           │
└─────────────────────────────────┘
```

원장 항목을 분기 헤더로 묶고, 각 분기 안에서 시간순으로 렌더한다. 표시 항목: 날짜 · 유형(매수/매도/재평가/보류) · 체결가 · 수량 · 금액 · 매도 사유 · 메모. 요약 한 줄은 `ledgerStats(h)`의 `buyCount·buyAmt·sellCount·sellAmt`를 그대로 쓴다 — 새 수식을 만들지 않는다.

### 4-4. 칸 회수 등재 강제

thesis 자동 등재 모드(`rjCtx.forceReason==='thesis'`)일 때만:

- `rj-close` 버튼과 배경 클릭으로 닫히지 않는다
- 재검토 트리거가 비어 있으면 저장을 거부한다 (PRD §4: "재검토 트리거 필수")

수동 기각 모달(`+ 후보 등록` 경유)은 현행 그대로 닫힌다.

**받아들인 마찰**: "일단 팔고 트리거는 나중에"가 막힌다. 사용자가 명시적으로 승인했다. 근거는 PRD §7-D15 부속 — 칸 회수는 이 시스템이 원본 펀치카드 대비 갖는 우위이고, 회수를 안 하면 그 우위가 소멸한다.

### 4-5. 기존 데이터는 자동 변환하지 않는다

이미 미등재로 청산된 종목(모달을 닫아버린 경우)은 조용히 등재하지 않는다. `pos`에 남되 배너를 단다:

> ⚠ 논지 훼손 전량매도 · 칸 회수 미등재 — `[등재하기]`

판정: `netShares<=0` **및** 마지막 매도의 `sellReason`이 `isThesisBroken()` (`1075`) **및** `!thesisRejectOf(h.id)`.

`[등재하기]`는 기존 칸 회수 모달을 같은 인자로 연다(`2166-2173`과 동일). 등재되면 다음 렌더부터 4-2 경로를 타고 사라진다.

### 4-6. 진행 바 음수 클램프

`1214`:

```js
const investedPct = targetAmt>0 ? Math.max(0, Math.min(100, st.netInvested/targetAmt*100)) : 0;
```

## 5. 엣지 케이스

| 상황 | 기대 동작 |
|---|---|
| 모든 종목이 청산됨 | `pos` 빈 배열 → `equityScale=0` → `cashWeight=1`. 목표 배분은 채권 100% |
| 칸 회수 항목을 14일 유예 내에 삭제 | `thesisRejectOf`가 `undefined` → 종목이 계획으로 복귀. 기각 취소의 자연스러운 의미이므로 허용 |
| 같은 이름으로 재진입 | 기존 동작 유지 — 새 `holdings` 행, 새 1칸 (PRD §7-D15) |
| 청산 종목의 기존 기록 `✎ 수정` | 카드가 일지에서 사라지므로 **접근 경로가 없어진다.** 4-3 모달은 읽기 전용이다. 오기입 정정이 필요하면 백업 JSON 편집 후 가져오기 — HANDOFF에 명시할 것 |

## 6. 검증 (P5)

Node DOM-stub 스크립트로 배포 전 확인. **2번은 실제 배분 숫자가 바뀌므로 손계산과 대조한다.**

1. 청산 종목이 `pos`에서 빠진다
2. 남은 종목의 목표 금액이 재정규화된다. **`posSum` 값에 따라 결과가 갈리므로 두 경우를 모두 손계산과 대조한다** (`목표 = rel × equityScale × 총원금`, `equityScale = min(posSum,1) × HALF`):
   - `posSum ≥ 1` — 목표가 **커진다**. 스크린샷이 이 경우다(채권 50% = `equityScale`가 `HALF`에 걸려 있다는 뜻) → `$6,482`보다 커져야 한다
   - `posSum < 1` — 목표가 **변하지 않는다**. `rel`이 커지는 만큼 `equityScale`가 줄어 정확히 상쇄된다. "항상 커진다"고 단정하면 이 경우에서 검증이 잘못 실패한다
3. `investedPct`가 음수 입력에서 `0`으로 클램프된다
4. 미등재 청산 종목은 `pos`에 남고 배너 판정이 참이 된다 (4-5)
5. 칸 회수 항목 삭제 시 종목이 `pos`로 복귀한다 (엣지 케이스)

브라우저 실기: 청산 종목이 두 탭에서 사라지는지, `[매매 이력]` 모달이 원장을 그대로 보여주는지, 강제 등재 모달이 트리거 없이 안 닫히는지.

## 7. 문서 갱신

- **PRD §4** 147행 — "청산된 historical 행에는 새 매수 기록을 막는다"가 낡는다. 청산 종목은 계획에서 사라지므로 문구를 바꾼다
- **PRD §7** — 결정 한 줄 추가 (D18): 청산 종목을 계획에서 제외, 회고 이력은 칸 회수 카드
- **`docs/superpowers/browser-checklist-rejection-ledger.md`**
  - 24행 — "배포본은 아직 옛날 버전"이 이미 낡았다(배포 완료). 이번에 함께 고친다
  - 112-113행 — "청산된 종목의 historical 행에서 새 매수 기록 시도 → 차단 메시지", "그 행의 기존 기록 `✎ 수정`은 여전히 열린다". 청산 행 자체가 사라지므로 두 항목 모두 성립하지 않는다. 검증 항목을 "두 탭에서 사라지는지"로 교체한다
- **HANDOFF** — 5절의 `✎ 수정` 접근 경로 상실을 함정으로 기록
