## 지금 상태

**켈리를 2-시나리오(상단/하단)에서 3-시나리오(Bull/Base/Bear)로 확장했다.** 구현 완료,
커밋 완료. `main`은 아직 이전 배포 상태(`3eaeaa5`) 그대로다 — **머지도 푸시도 안 했다.**

설계는 `docs/superpowers/specs/2026-08-13-kelly-three-scenario-design.md`, 계획은
`docs/superpowers/plans/2026-08-13-kelly-three-scenario.md`. 결정 기록은 PRD §7-D20.

**배포하면 폰에서 무슨 일이 벌어지는지 먼저 알아야 한다**: v4→v5 마이그레이션은 `base`를
채우지 않는다(의도된 forcing function, §7-D20). 그 결과 **기존 보유 종목 전부가 동시에
켈리 보류 상태가 되어 목표 배분·분기 매매일지가 한꺼번에 빈다.** 사용자가 Base를 채울
시간을 낼 수 있는 타이밍인지 판단한 뒤 머지·배포할 것 — 지금 바로 배포하면 다음에 폰을
열었을 때 계획 화면이 비어 있는 걸 예고 없이 보게 된다.

### 무엇이 바뀌었나

- 종목마다 `up`(Bull)·`base`(Base)·`down`(Bear) 목표가와 `prob`(P(Bull))·`pBase` 확률을
  받는다. `pBear = 1 − prob − pBase`는 도출만 하고 저장하지 않는다.
- 켈리 수식이 3-결과 닫힌해로 바뀌었다(`kelly3`, PRD §4.4). `base`를 현재가·확률 0으로
  두면 정확히 옛 2-시나리오 공식 `f = p/a − q/b`로 축퇴한다 — 이 축퇴 성질이 그대로
  롤백 경로다(아래 "되돌리는 법").
- 입력 3행이 **종목 추가 폼·재평가(📊)·수정(✎)** 세 곳에 공통으로 들어간다. 확률 합
  100% 검증과 `Bull ≥ Base ≥ Bear` 순서 검증이 저장을 막는다.
- Base 미입력 종목은 `⚠ Base 미입력 — 켈리 보류` 배너를 달고 배분에서 빠지되, 살아있는
  종목의 목표가를 줄이지 않는다(§7-D18과 같은 형태의 회귀 검증).
- 스냅샷 `v:4` → `v:5`. 마이그레이션은 버전 표기만 갱신하고 `base`는 채우지 않는다.

## 알아야 할 것

- **PBR로 입력하면 켈리 값(`f`)은 맞지만 주수가 틀린다.** 켈리는 비율이라 스케일
  불변이지만, 매수 금액을 주가로 나누는 주수 계산은 스케일에 의존한다. TSMC처럼
  분석 문서가 PBR 단위면 **BPS로 환산한 달러(`$`) 값**을 입력할 것. 자동 환산은
  만들지 않았다(BPS는 분기마다 변한다 — 안 만드는 것, PRD §4.4/설계 문서 참조).
- **종목마다 시나리오 도달 기간 관점을 맞춰야 `f` 비교가 유효하다.** 도구는 기간을
  묻지 않는다 — 3년 관점 종목과 15년 관점 종목을 같은 `posSum`에 넣으면 상대 배분이
  왜곡된다. 연율화하지 않는 것도 의도다(설계 문서 «켈리 전제와 한계» §1).
- **입력 레이아웃이 스펙 목업과 다르게 렌더된다.** `.prob-in{width:64px}`가
  `.fld input{width:100%}`에 밀려(특정성 0,1,0 vs 0,1,1) 목표가·확률이 나란히가 아니라
  **위아래로 쌓인 동일 너비 입력 두 칸**으로 나온다(측정: 추가 폼 134/134px, 수정 모달
  95/95px, 재평가 모달 402/402px — 헤드리스 500px 뷰포트 기준이라 실제 폰 폭은 아직
  미검증). CSS를 고치라는 요청은 없었으므로 그대로 뒀다 — 체크리스트 2단계에 이 모양
  그대로 폰에서 라벨이 헷갈리지 않는지 보는 항목을 넣어뒀다.
- **`kelly3`의 근 선택 안전망(`filter(inDomain)` + tie-break)은 기존 8개 픽스처로는
  전혀 검증되지 않았다.** 돌연변이 테스트로 확인: `up ≥ base ≥ down` 순서가 성립하는
  입력에서는 두 근 중 `(-B-s)/(2A)` 쪽만 유효 근이 될 수 있다는 게 수만 회 무작위
  탐색으로 확인된 수학적 성질이라, "잘못된 근을 고른다"는 형태의 돌연변이는 걸리지
  않는다. 대신 `test_pipeline.js`에 **세 rᵢ가 전부 같은 부호(예: 모든 시나리오가
  현재가 아래)면 목적함수가 무계(無界)라 유효근이 없는** 케이스를 하나 추가해 그
  안전망이 실제로 하는 일(빈 배열 → `null`)을 검증하게 했다 — `test_pipeline.js`는
  이제 **98 pass**다(브리프의 "97 pass"는 이 추가 전 숫자).
- **설계 문서 §"모든 rᵢ ≤ 0" 행과 실제 동작이 어긋난다.** 설계 문서는 "f < 0 정상 반환
  → §7-D6 배분 제외"라고 적었지만, 실측(TSMC 현재가 PBR 10.5, 목표가 8.04/5.70/3.05
  전부 하회)으로는 `kellyOf`가 `err:'시나리오가 퇴화했습니다'`를 반환한다 — 세 rᵢ가
  전부 음수면 `f→−∞`로 목적함수가 무계라 유효 극점이 없기 때문(수학적으로 타당한
  동작이다: 확실히 다 하락하는 자산은 무한 공매도가 "최적"이 되는 퇴화 상황). 결과
  자체는 배분에서 빠지므로 사용자 눈에 보이는 결과("이 종목은 배분 안 됨")는 같지만,
  에러 문구가 "하방 시나리오가 없습니다"류가 아니라 "퇴화했습니다"로 나온다. 알고리즘은
  건드리지 않았다 — 설계 의도와 다른 문구가 뜨는 게 재검토할 일인지는 다음 세션/사용자
  판단.

- **F1 — 추가 폼만 목표가 양수 검사가 없었다.** `상단 400 · Base 50 · 하단 −10` 이

  ✎·📊 에 넣으면 거부된다. 세 화면이 이제 같은 규칙을 쓴다(`:1189`/`:2514`/`:2599`).

  +1.6085 → −0.1975 로 비활성이 되는데, 옛 판별은 `false` 라 **'가격 상승/밸류에이션
  부담'(분할 매도 허용)** 이라는 정반대 조언이 떴다. 이제 P(Bear) 상승을 본다.
- F2 `reDelta` 가드·`changeStr`(Base 변경을 '변경 없음' 으로 표시하던 것), F3
  `.prob-in` 의 죽은 `margin-left:8px`(그리드 간격 7px 대비 8px 오버행) 도 함께 고쳤다.
- **이월(문서화만)**: 화면 문구 5곳이 아직 "승률·상단·하단" 표현이다. `readProb()` 는
  호출처 0인 기존 죽은 코드다(삭제하지 않음). 커밋 제목 2건이 50자를 넘는다.

## 손대지 말 것

- **`kellyOf`의 선언 형태**(`function kellyOf(h){`) — `test_pipeline.js`의 `grab()`이
  중괄호 균형으로 이 형태를 찾는다. 화살표 함수나 다른 선언 방식으로 바꾸면 테스트가
  통째로 죽는다.
- **`kelly3`의 `α≈0 ∧ β≈0` 가드**(`if(Math.abs(A)<1e-12){ if(Math.abs(B)<1e-12) return null; ...}`).
  `p_base=1`처럼 "확실히 제자리"인 입력에서 0/0을 막는 유일한 장치다.
- **`thinDown`이 `Math.abs(Math.min(...rs))` 기준인 것.** 하단 칸(`rs[2]`)이 아니라
  세 시나리오 중 최솟값 기준이어야 한다 — 순서 검증이 있는 한 수학적으로는 `rs[2]`와
  같지만(돌연변이 C로 확인, 방어적 코드), 순서 검증 자체가 미래에 느슨해지면 이 기준이
  마지막 방어선이 된다.
- **`kellyOf`의 순서 검증**(`if(!(rs[0]>=rs[1] && rs[1]>=rs[2])) return {...err:'상단 ≥ Base ≥ 하단이 아닙니다'}`).
  Base·Bear를 바꿔 적어도 수학은 조용히 돌아간다 — 화면의 "Base" 라벨이 거짓말하는 걸
  막는 **유일한** 장치다. 돌연변이 테스트로 직접 확인: 이 줄을 지우면 딱 이 검증
  테스트 하나만 FAIL한다.
- **`thesisWorsened` 의 `prevPBase!==undefined` 가드**(`index_kelly.html:1401`).
  Task 이전 원장 항목에는 `prevPBase` 가 없어, 가드를 빼면 `NaN` 비교가 조용히
  false 가 되거나 레거시 항목을 오분류한다.
- **마이그레이션에 기본값을 채우지 말 것.** v4→v5는 스냅샷 버전 표기만 갱신하고
  `base`는 비워둔다. 추정값을 채우면 "아무도 생각한 적 없는 숫자"가 조용히 배분을
  움직인다 — 이번 확장 전체의 forcing function이 무의미해진다.

## 되돌리는 법 — ⚠ 데이터가 안전하지 않다

브랜치를 머지·푸시하지 않았으므로 **지금은** 되돌릴 게 없다. 문제는 배포한 **뒤**다.

**`prob` 필드의 의미가 바뀌었다.** v4에서는 "승률"(나머지 1−p가 전부 하단)이고,
v5에서는 "P(Bull)"(나머지가 Base와 Bear로 나뉜다). 필드 이름과 타입이 같아서 옛 빌드가
**에러 없이 읽고 조용히 다르게 해석한다.**

실측 — 현재가 100 · Bull 150(25%) · Base 120(50%) · Bear 70(25%) 종목:

| 빌드 | f | 결과 |
|---|---|---|
| 새(3-시나리오) | **1.6085** | 배분에 포함 |
| 옛(같은 데이터) | **−0.6667** | **음수 켈리로 배분에서 제외** |

그래서 **배포 후 코드만 revert 하면 데이터가 오독된다.** 종목이 계획에서 통째로
사라지는데 경고가 없다. 이전 기능들(검토 필드·논지 승계)은 순수 추가 필드라 롤백이
안전했지만 **이번엔 아니다.**

되돌리려면 순서가 있다:

1. 폰에서 `⬇ 내보내기`로 v5 백업을 받아둔다 (나중에 다시 켤 때 필요하다)
2. 코드를 revert 해서 배포한다
3. **v5 이전 백업으로 `⬆ 가져오기`** 하거나, 각 종목의 `prob`을 옛 의미(승률)로
   손으로 고친다. 안 하면 종목들이 배분에서 사라진 채로 남는다

계산 수준의 롤백(코드는 새 빌드, 값만 옛 공식으로)은 `kelly3`에 `p_base=0, r_base=0`을
넘기면 정확히 같은 값이 나온다 — 축퇴 성질이 그 경로를 겸한다(설계 문서, PRD §7-D20).

**교훈**: 필드를 추가하는 것과 기존 필드의 **의미**를 바꾸는 것은 다르다. 후자는
스냅샷 버전만으로 방어되지 않는다 — 옛 빌드는 버전을 보고 거부하지 않고 그냥 읽는다.
