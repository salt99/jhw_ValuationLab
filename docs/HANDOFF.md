## 지금 상태

**총노출을 하프 켈리에서 풀 켈리로 바꾸고 배포했다.** `29b5e50..84d0a9b` 푸시 완료.

직전 작업(3-시나리오 확장, §7-D20)은 **폰 실기 검증까지 끝났다** — 사용자가 "이상없음"
확인. 그 검증 중에 나온 질문("왜 주식이 50%까지만 되고 나머지가 채권이지?")이 이번
변경의 출발점이다. 사용자는 50% 상한을 **켈리 계산 결과**로 알고 있었는데, 실제로는
도구가 임의로 건 안전계수(`HALF=0.5`)였다. 오해를 풀고 나서 풀 켈리를 택했다.

`feat/kelly-three-scenario` 브랜치가 아직 원격에 있다 — `main`에 병합된 내용이라 지워도 된다.

### 무엇이 바뀌었나

```js
const HALF=0.5;                              // 삭제
const equityScale=Math.min(posSum,1)*HALF;   // 이전
const equityScale=Math.min(posSum,1);        // 지금 (index_kelly.html:970)
```

- 양수 켈리 합이 1을 넘으면 **주식 100%·채권 0%**. 합이 1 미만이면 그대로다
  (켈리 합 13% → 주식 13%·채권 87%).
- **상대 배분은 안 바뀐다.** 원래부터 풀 켈리 정규화였고(§7-D5) 공통 계수는 약분되므로,
  각 종목 목표비중이 정확히 2배가 될 뿐 종목 간 비율은 동일하다.
- 화면 문구 4곳(태그라인 · 요약박스 `Half-Kelly`→`풀 켈리` · 설명 노트의 `× ½` · 켈리 합
  초과 경고)과 `test_pipeline.js` 의 0.5 하드코딩 6곳을 함께 고쳤다.
- 결정 기록은 PRD §7-D22. §7-D5 는 남기되 "총노출 부분은 D22로 대체됨"을 표기했다.

## 알아야 할 것

- **⚠ 보유 종목이 2개 이하면 40% 개별 상한이 작동하지 않는다.** 이번 변경이 만든 구멍이다.
  `compute()` 의 상한 재분배는 `relCap × 종목수 ≥ 1` 일 때만 도는데, `equityScale=1` 이면
  `relCap = MAX_SINGLE/1 = 0.40` 이라 2종목에서 `0.8 < 1` 로 통째로 건너뛴다. 하프 켈리
  때는 `relCap = 0.80` 이라 2종목에서도 걸렸다. **실측**: 같은 입력에서 2종목이면 한
  종목이 64.10%, 3종목이면 정상적으로 40.00% 에서 잘린다. 지금 3종목이라 당장은 정상이나
  **칸 회수로 2종목이 되면 경고 없이 풀린다**(`anyCapped` 가 false 라 경고도 안 뜬다).
  고치려면 상한을 `rel` 이 아니라 최종 비중에 걸고 초과분을 채권으로 보내야 하는데, 그러면
  그 경우엔 주식이 100%가 안 된다 — 사용자 요청("100%")과 상충해서 손대지 않았다. PRD
  §7-D22 에 대가로 적어뒀다. 다음 세션이 다시 꺼낼 만한 후보다.
- **채권 0% 면 8분기 분할매수의 "매수 대기 실탄"이 사라진다.** 분할 속도가 남은 분기 수로만
  통제된다. 도구 화면의 "채권은 매수 대기 실탄입니다" 문구는 켈리 합이 1 미만일 때만 참이다.
- **PBR로 입력하면 켈리 값(`f`)은 맞지만 주수가 틀린다.** 켈리는 비율이라 스케일 불변이지만,
  매수 금액을 주가로 나누는 주수 계산은 스케일에 의존한다. TSMC처럼 분석 문서가 PBR
  단위면 **BPS로 환산한 달러(`$`) 값**을 입력할 것. 자동 환산은 만들지 않았다(BPS는 분기마다
  변한다 — 안 만드는 것, PRD §4.4/설계 문서 참조).
- **종목마다 시나리오 도달 기간 관점을 맞춰야 `f` 비교가 유효하다.** 도구는 기간을 묻지
  않는다 — 3년 관점 종목과 15년 관점 종목을 같은 `posSum`에 넣으면 상대 배분이 왜곡된다.
  연율화하지 않는 것도 의도다(설계 문서 «켈리 전제와 한계» §1). **풀 켈리로 바뀌면서 이
  왜곡의 대가가 2배가 됐다.**
- **입력 레이아웃이 스펙 목업과 다르게 렌더된다.** `.prob-in{width:64px}` 가
  `.fld input{width:100%}` 에 밀려(특정성 0,1,0 vs 0,1,1) 목표가·확률이 나란히가 아니라
  **위아래로 쌓인 동일 너비 입력 두 칸**으로 나온다. 사용자가 폰에서 보고 "이상없음"
  했으므로 실사용상 문제는 없다고 판단됐다 — 고치라는 요청은 없었다.
- **설계 문서 §"모든 rᵢ ≤ 0" 행과 실제 동작이 어긋난다.** 설계 문서는 "f < 0 정상 반환 →
  §7-D6 배분 제외"라고 적었지만, 실측으로는 `kellyOf` 가 `err:'시나리오가 퇴화했습니다'`
  를 반환한다 — 세 rᵢ가 전부 음수면 `f→−∞` 로 목적함수가 무계라 유효 극점이 없기 때문.
  배분에서 빠지는 결과는 같고 에러 문구만 다르다. 알고리즘은 안 건드렸다.
- **`readProb()` 는 호출처 0인 죽은 코드다**(`index_kelly.html:996` 부근). 기존 코드라
  삭제하지 않았다(CLAUDE.md §3). 지울 거면 별도 커밋으로.

## 손대지 말 것

- **`kellyOf` 의 선언 형태**(`function kellyOf(h){`) — `test_pipeline.js` 의 `grab()` 이
  중괄호 균형으로 이 형태를 찾는다. 화살표 함수로 바꾸면 테스트가 통째로 죽는다.
  `compute`·`kelly3`·`livePlanHoldings`·`isThesisReject` 도 같다.
- **`test_pipeline.js:31` 의 `constOf(...)` 목록** — 이제 `MAX_SINGLE`·`THIN_DOWNSIDE`
  둘뿐이다. `HALF` 를 지우면서 함께 뺐다. 여기 없는 상수를 `compute()` 에서 참조하면
  테스트가 `ReferenceError` 로 죽는다.
- **`kelly3` 의 `α≈0 ∧ β≈0` 가드**(`if(Math.abs(A)<1e-12){ if(Math.abs(B)<1e-12) return null; ...}`).
  `p_base=1` 처럼 "확실히 제자리"인 입력에서 0/0을 막는 유일한 장치다.
- **`thinDown` 이 `Math.abs(Math.min(...rs))` 기준인 것.** 하단 칸(`rs[2]`)이 아니라 세
  시나리오 중 최솟값 기준이어야 한다 — 순서 검증이 있는 한 수학적으로는 `rs[2]` 와
  같지만(돌연변이 C로 확인, 방어적 코드), 순서 검증이 미래에 느슨해지면 마지막 방어선이 된다.
- **`kellyOf` 의 순서 검증**(`if(!(rs[0]>=rs[1] && rs[1]>=rs[2])) return {...err:'상단 ≥ Base ≥ 하단이 아닙니다'}`).
  Base·Bear를 바꿔 적어도 수학은 조용히 돌아간다 — 화면의 "Base" 라벨이 거짓말하는 걸 막는
  **유일한** 장치다. 돌연변이 테스트로 확인: 이 줄을 지우면 딱 그 검증 하나만 FAIL한다.
- **`thesisWorsened` 의 `prevPBase!==undefined` 가드**(`index_kelly.html:1400`).
  3-시나리오 이전 원장 항목에는 `prevPBase` 가 없어, 가드를 빼면 `NaN` 비교가 조용히
  false 가 되거나 레거시 항목을 오분류한다.
- **마이그레이션에 기본값을 채우지 말 것.** v4→v5는 스냅샷 버전 표기만 갱신하고 `base` 는
  비워둔다. 추정값을 채우면 "아무도 생각한 적 없는 숫자"가 조용히 배분을 움직인다 —
  3-시나리오 확장 전체의 forcing function 이 무의미해진다.

## 미결 — 다음 세션이 이어받을 것

1. **각 보유 종목의 Base 채우기** — 폰에서 `✎ 수정`으로 하나씩. 다 채울 때까지 그 종목의
   목표 배분이 비어 있다. 3종목은 채워진 것으로 확인됐다(사용자 "3개 종목추가했는데").
2. **풀 켈리 화면 확인** — 폰에서 `주식 목표 100% · 채권 0%`, 배분바에 채권(민트) 구간
   없음, 요약박스 라벨 `풀 켈리`. 헤드리스로는 확인했으나 실기는 아직.
3. **2종목 40% 상한 구멍**(위 "알아야 할 것" 첫 항목) — 고칠지 말지 판단이 필요하다.
4. **밀린 폰 검증**(검토 필드, §7-D19) — 진행 체크박스 줄바꿈, 계기 줄 스타일,
   `✎ 메모` 모달 스타일. 체크리스트: `docs/superpowers/browser-checklist-rejection-ledger.md`.
5. **화면 문구 드리프트** — 설명 노트의 켈리 공식이 아직 2-시나리오 `f = p/a − q/b` 다
   (`index_kelly.html:417`). "승률·상단·하단" 표현도 몇 곳 남았다.

### ⚠ 3-시나리오까지 되돌리기 — 데이터가 안전하지 않다

**`prob` 필드의 의미가 바뀌었다.** v4에서는 "승률"(나머지 1−p가 전부 하단)이고, v5에서는
"P(Bull)"(나머지가 Base와 Bear로 나뉜다). 필드 이름과 타입이 같아서 옛 빌드가 **에러 없이
읽고 조용히 다르게 해석한다.**

실측 — 현재가 100 · Bull 150(25%) · Base 120(50%) · Bear 70(25%) 종목:

| 빌드 | f | 결과 |
|---|---|---|
| 새(3-시나리오) | **1.6085** | 배분에 포함 |
| 옛(같은 데이터) | **−0.6667** | **음수 켈리로 배분에서 제외** |

종목이 계획에서 통째로 사라지는데 경고가 없다. 되돌리려면 순서가 있다:

1. 폰에서 `⬇ 내보내기`로 v5 백업을 받아둔다 (나중에 다시 켤 때 필요하다)
2. 코드를 revert 해서 배포한다
3. **v5 이전 백업으로 `⬆ 가져오기`** 하거나, 각 종목의 `prob` 을 옛 의미(승률)로 손으로
   고친다. 안 하면 종목들이 배분에서 사라진 채로 남는다

계산 수준의 롤백(코드는 새 빌드, 값만 옛 공식으로)은 `kelly3` 에 `p_base=0, r_base=0` 을
넘기면 정확히 같은 값이 나온다 — 축퇴 성질이 그 경로를 겸한다(PRD §7-D20).

**교훈**(§7-D21): 필드를 **추가**하는 것과 기존 필드의 **의미**를 바꾸는 것은 다르다.
후자는 스냅샷 버전만으로 방어되지 않는다 — 옛 빌드는 버전을 보고 거부하지 않고 그냥 읽는다.
