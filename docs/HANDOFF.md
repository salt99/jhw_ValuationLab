## 지금 상태

**켈리 사이징을 두 번 고쳤다.** `29b5e50..5079bfa` 푸시 완료.
라이브: `https://salt99.github.io/jhw_ValuationLab/index_kelly.html`

1. **총노출을 하프 켈리 → 풀 켈리**(§7-D22, `84d0a9b`)
2. **개별 상한 40%→30%, 초과분을 다른 종목이 아니라 채권으로**(§7-D23, `5079bfa`)

둘은 이어진 하나의 흐름이다. 1번이 "종목이 1~2개여도 주식 100%"를 만들었고, 사용자가
바로 그 지점("1~2개만 추가되었을 때 과도하게 포션을 잡는 것")을 우려해 2번으로 갔다.
**2번만 따로 읽으면 왜 상한을 조였는지 알 수 없다.**

이어서 **종목 식별색**을 넣었다(§7-D24). 배분바 세그먼트가 전부 `--accent` 라 종목이
인접하면 한 덩어리로 보였다. 색은 종목 id 로 매핑해 배분바와 카드 왼쪽 띠가 같은 색을
쓴다. 화면 확인용 데모 데이터도 **고정 픽스처**로 못박았다(§7-D25).

직전 작업(3-시나리오 확장, §7-D20)은 **폰 실기 검증까지 끝났다** — 사용자가 "이상없음"
확인. 그 검증 중에 나온 질문("왜 주식이 50%까지만 되고 나머지가 채권이지?")이 이번
변경의 출발점이다. 사용자는 50% 상한을 **켈리 계산 결과**로 알고 있었는데, 실제로는
도구가 임의로 건 안전계수(`HALF=0.5`)였다. 오해를 풀고 나서 풀 켈리를 택했다.

`feat/kelly-three-scenario` 브랜치가 아직 원격에 있다 — `main`에 병합된 내용이라 지워도 된다.

### 무엇이 바뀌었나

`compute()` 가 이렇게 됐다 (`index_kelly.html:964`):

```js
const raw=Math.min(posSum,1);            // 풀 켈리 — HALF=0.5 삭제됨
pos.forEach(r=>{
  const w=posSum>0?r.k.f/posSum*raw:0;
  r.capped=w>MAX_SINGLE+1e-9;
  r.w=Math.min(w,MAX_SINGLE);            // 초과분은 어디로도 안 간다
});
const equityScale=pos.reduce((s,r)=>s+r.w,0);
pos.forEach(r=>r.rel=equityScale>0?r.w/equityScale:0);
```

- **주식 노출이 종목 수에 따라 올라가는 사다리가 된다.** 실측(켈리 고른 배치):
  1종목 30% · 2종목 60% · 3종목 90% · **4종목부터 100%**. 켈리가 쏠린 배치면 더 낮다.
- **`equityScale` 이 더는 `min(posSum,1)` 이 아니다.** 상한을 자른 뒤의 합이라 상한이
  걸리면 주식 총비중 자체가 줄어든다. 구 방식에서 상한은 종목끼리 재분배만 했고 총비중은
  안 건드렸다 — 이 차이가 이번 변경의 핵심이다.
- **`rel` 의 의미는 유지했다.** `rel = w/equityScale` 이라 `rel × equityScale = 최종비중`
  항등식이 그대로 성립한다. 그래서 이 값을 쓰는 렌더 4곳(`:1290`·`:1312`·`:1362`·`:2269`)은
  한 줄도 안 고쳤다. **이 항등식을 깨면 화면 숫자가 조용히 틀린다.**
- **상한 아래에서는 켈리가 전부 결정한다.** 실측: 상한 미적용 종목들은 켈리 몫이 그대로
  최종비중이 되고, 상호 비율도 켈리 비율과 소수점 6자리까지 일치한다.
- 30% 근거: 5종목 균등비중(20%)의 **1.5배**. 20% 로 잡으면 균등비중과 같아져 켈리가
  확신 차이를 표현할 여지가 사라진다(균등배분 축퇴).
- 화면 문구 6곳과 `test_pipeline.js` 를 함께 고쳤다. 결정 기록은 PRD §7-D22·D23,
  §7-D5(총노출)·§7-D7(캡 수치·재배분)에 대체 표기를 달았다.

## 알아야 할 것

- **⚠ 설계 문서 3곳이 코드와 어긋난다 — 소급 수정하지 않았다.**
  `docs/superpowers/specs/2026-08-13-kelly-three-scenario-design.md` 의 `:106`
  "`MAX_SINGLE`(40%)", `:121` "Half-Kelly 는 총노출 결정에만 관여한다", `:129`
  "`equityScale = min(posSum,1)×0.5`" 는 **전부 D22·D23 으로 대체됐다.** 날짜 붙은 설계
  문서는 그 시점의 판단 기록이라 고치지 않는 게 맞다고 판단했으나, 안 적어두면 다음 세션이
  스펙을 읽고 40%·하프 켈리를 현재 사실로 믿는다. **정본은 PRD §4.4 와 코드다.**
- **엄밀한 의미의 "제약 하 켈리"는 아니다.** 진짜 제약 하 log-optimal 이라면 `w ≤ 0.30`
  을 걸고 다시 최적화해야 하고, 그러면 남는 여력이 채권이 아니라 **다른 주식으로** 간다.
  지금은 "켈리를 푼 다음 자른다"이고 구 재분배가 오히려 그쪽에 가까웠다. 다만 도구는 애초에
  진짜 다자산 켈리가 아니다 — 설계 문서 §4 "종목 간 상관관계를 무시한다. 진짜 다자산
  켈리는 공분산이 필요하다". 각 종목 `f` 를 따로 풀어 정규화하는 것 자체가 휴리스틱이라
  "제약 하 최적화"를 따질 기반이 없다. **상한의 역할은 켈리를 정확하게 만드는 게 아니라
  켈리가 못 보는 것(왼쪽 꼬리·상관관계)을 상쇄하는 것**이고(설계 문서 §3), 그렇다면 잘라낸
  초과분을 역시 켈리로 추정된 다른 종목에 넘기는 건 과대평가를 옮기기만 하는 셈이다.
  이게 채권으로 보내기로 한 이유다. 되돌리려는 다음 세션은 이 문단을 먼저 읽을 것.
- **채권이 0% 가 되면 8분기 분할매수의 "매수 대기 실탄"이 사라진다.** 분할 속도가 남은
  분기 수로만 통제된다. 상한 덕에 종목이 4개 미만이면 채권이 남으므로 초기에는 문제가
  덜하지만, 4종목 이상에서 켈리가 고르면 채권 0% 가 된다.
- **PBR로 입력하면 켈리 값(`f`)은 맞지만 주수가 틀린다.** 켈리는 비율이라 스케일 불변이지만,
  매수 금액을 주가로 나누는 주수 계산은 스케일에 의존한다. TSMC처럼 분석 문서가 PBR
  단위면 **BPS로 환산한 달러(`$`) 값**을 입력할 것. 자동 환산은 만들지 않았다(BPS는 분기마다
  변한다 — 안 만드는 것, PRD §4.4/설계 문서 참조).
- **종목마다 시나리오 도달 기간 관점을 맞춰야 `f` 비교가 유효하다.** 도구는 기간을 묻지
  않는다 — 3년 관점 종목과 15년 관점 종목을 같은 `posSum`에 넣으면 상대 배분이 왜곡된다.
  연율화하지 않는 것도 의도다(설계 문서 «켈리 전제와 한계» §1). **풀 켈리로 바뀌면서 이
  왜곡의 대가가 2배가 됐다.**
- **입력 레이아웃이 스펙 목업과 다르게 렌더된다.** `.prob-in{width:64px}` 가
  `.fld input{width:100%}` 에 밀려(특정성 0,1,0 vs 0,1,1) 목표가·확률이 나란히가 아니라
  **위아래로 쌓인 동일 너비 입력 두 칸**으로 나온다. 사용자가 폰에서 보고 "이상없음"
  했으므로 실사용상 문제는 없다고 판단됐다 — 고치라는 요청은 없었다.
- **설계 문서 §"모든 rᵢ ≤ 0" 행과 실제 동작이 어긋난다.** 설계 문서는 "f < 0 정상 반환 →
  §7-D6 배분 제외"라고 적었지만, 실측으로는 `kellyOf` 가 `err:'시나리오가 퇴화했습니다'`
  를 반환한다 — 세 rᵢ가 전부 음수면 `f→−∞` 로 목적함수가 무계라 유효 극점이 없기 때문.
  배분에서 빠지는 결과는 같고 에러 문구만 다르다. 알고리즘은 안 건드렸다.
- **`readProb()` 는 호출처 0인 죽은 코드다**(`index_kelly.html:996` 부근). 기존 코드라
  삭제하지 않았다(CLAUDE.md §3). 지울 거면 별도 커밋으로.

## 손대지 말 것

- **`kellyOf` 의 선언 형태**(`function kellyOf(h){`) — `test_pipeline.js` 의 `grab()` 이
  중괄호 균형으로 이 형태를 찾는다. 화살표 함수로 바꾸면 테스트가 통째로 죽는다.
  `compute`·`kelly3`·`livePlanHoldings`·`isThesisReject` 도 같다.
- **`test_pipeline.js:31` 의 `constOf(...)` 목록** — 이제 `MAX_SINGLE`·`THIN_DOWNSIDE`
  둘뿐이다. `HALF` 를 지우면서 함께 뺐다. 여기 없는 상수를 `compute()` 에서 참조하면
  테스트가 `ReferenceError` 로 죽는다.
- **`kelly3` 의 `α≈0 ∧ β≈0` 가드**(`if(Math.abs(A)<1e-12){ if(Math.abs(B)<1e-12) return null; ...}`).
  `p_base=1` 처럼 "확실히 제자리"인 입력에서 0/0을 막는 유일한 장치다.
- **`thinDown` 이 `Math.abs(Math.min(...rs))` 기준인 것.** 하단 칸(`rs[2]`)이 아니라 세
  시나리오 중 최솟값 기준이어야 한다 — 순서 검증이 있는 한 수학적으로는 `rs[2]` 와
  같지만(돌연변이 C로 확인, 방어적 코드), 순서 검증이 미래에 느슨해지면 마지막 방어선이 된다.
- **`kellyOf` 의 순서 검증**(`if(!(rs[0]>=rs[1] && rs[1]>=rs[2])) return {...err:'상단 ≥ Base ≥ 하단이 아닙니다'}`).
  Base·Bear를 바꿔 적어도 수학은 조용히 돌아간다 — 화면의 "Base" 라벨이 거짓말하는 걸 막는
  **유일한** 장치다. 돌연변이 테스트로 확인: 이 줄을 지우면 딱 그 검증 하나만 FAIL한다.
- **`thesisWorsened` 의 `prevPBase!==undefined` 가드**(`index_kelly.html:1400`).
  3-시나리오 이전 원장 항목에는 `prevPBase` 가 없어, 가드를 빼면 `NaN` 비교가 조용히
  false 가 되거나 레거시 항목을 오분류한다.
- **마이그레이션에 기본값을 채우지 말 것.** v4→v5는 스냅샷 버전 표기만 갱신하고 `base` 는
  비워둔다. 추정값을 채우면 "아무도 생각한 적 없는 숫자"가 조용히 배분을 움직인다 —
  3-시나리오 확장 전체의 forcing function 이 무의미해진다.
- **`compute()` 의 `rel = w/equityScale` 한 줄.** 렌더 4곳이 `rel × equityScale` 로
  최종비중을 복원한다. `rel` 을 켈리 몫(`f/posSum`)으로 되돌리면 상한이 걸린 종목의 화면
  숫자가 조용히 커진다 — 테스트 `상한 — rel × equityScale 항등식` 그룹이 이걸 지킨다.
- **종목 색을 `colorOf` 맵(종목 id 기준)으로 매기는 것**(`index_kelly.html:1286`).
  배분바는 `pos`(켈리 양수만), 카드는 `rows`(보류·음수 포함)를 돌기 때문에 각자 인덱스로
  매기면 보류 종목이 끼는 순간 그 뒤가 통째로 밀린다. **예외가 안 나고 화면만 조용히
  거짓말한다.** 자체 검사 25번이 이걸 지키고, 인덱스 매핑으로 되돌리는 돌연변이가 2건을
  FAIL 시키는 것까지 확인했다.
- **`--demo` 픽스처 값**(`docs/superpowers/build-selfcheck.js`). 고정 픽스처라 값이 바뀌면
  화면 비교의 기준이 사라진다(§7-D25). 바꿔야 하면 그 파일 주석의 기대 배분표와
  체크리스트 2단계의 표를 **함께** 갱신할 것 — 세 곳이 같은 숫자를 말해야 한다.

## 미결 — 다음 세션이 이어받을 것

1. **폰 실기 확인** — 3종목이면 `주식 목표 90% · 채권 10%` 근처가 나와야 한다(켈리가
   고를 때). 배분바에 채권 구간이 다시 생기고, 상한에 걸린 종목엔 `상한 30%` 태그와
   `초과분은 다른 종목이 아니라 채권으로 갔습니다` 경고가 뜬다. **종목 색이 실제 폰
   패널·조명에서 구분되는지**도 여기서만 확인된다 — ΔE 38 이상으로 계산했지만 계산은
   화면 밝기를 모른다. 체크리스트 2단계에 항목을 넣어뒀다.
2. **각 보유 종목의 Base 채우기** — 폰에서 `✎ 수정`으로 하나씩. 3종목은 채워진 것으로
   확인됐다(사용자 "3개 종목추가했는데").
3. **목표 종목 수는 5개, 방어선은 3개**로 이야기가 정리됐다(미확정). 근거: 5종목 균등이
   각 20% 라 상한 30% 가 확신 배율 1.5배를 남긴다. 다음 종목은 **반도체 밖에서** 찾는 게
   좋다 — 인적자본(반도체 커리어)이 이미 1칸이다(PRD §P8). 도구는 상관관계를 못 보므로
   후보 파이프라인의 `factor`(팩터 중복) 기각이 그 판단을 사람에게 맡겨둔 자리다.
4. **밀린 폰 검증**(검토 필드, §7-D19) — 진행 체크박스 줄바꿈, 계기 줄 스타일,
   `✎ 메모` 모달 스타일. 체크리스트: `docs/superpowers/browser-checklist-rejection-ledger.md`.
5. **화면 문구 드리프트** — 설명 노트의 켈리 공식이 아직 2-시나리오 `f = p/a − q/b` 다
   (`index_kelly.html:417`). "승률·상단·하단" 표현도 몇 곳 남았다.
6. **피셔의 분산 관련 원문 확인** — 과분산을 반대하고 기업 유형별 최소 보유 수를 제시한
   것까지는 확실하나 **정확한 숫자는 확인되지 않았다.** P1(출처 검증)이 non-negotiable 이고
   오귀속 3건 이력이 있으므로, 확인 전에는 PRD·화면 어디에도 숫자를 적지 않는다.

## 되돌리는 법

### 사이징 변경 되돌리기 — 데이터 안전

**저장 데이터 형식이 안 바뀌었으므로 코드만 되돌리면 된다.** `git revert` 로 충분하다.

- 상한만: `git revert 5079bfa` — 40% 재분배 방식으로 돌아간다(2종목 구멍도 함께 돌아온다)
- 풀 켈리까지: `git revert 5079bfa 84d0a9b` — 하프 켈리·40% 재분배로 완전 복귀
- **상한 수치만 바꾸고 싶으면** `MAX_SINGLE`(`index_kelly.html:905`) 한 줄이다. 다만
  `test_pipeline.js` 의 `상한 —` 세 그룹이 0.30 을 상수로 박아두었으므로 함께 고쳐야
  한다. 그게 의도다 — 사이징이 조용히 바뀌면 안 된다.

### ⚠ 3-시나리오까지 되돌리기 — 데이터가 안전하지 않다

**`prob` 필드의 의미가 바뀌었다.** v4에서는 "승률"(나머지 1−p가 전부 하단)이고, v5에서는
"P(Bull)"(나머지가 Base와 Bear로 나뉜다). 필드 이름과 타입이 같아서 옛 빌드가 **에러 없이
읽고 조용히 다르게 해석한다.**

실측 — 현재가 100 · Bull 150(25%) · Base 120(50%) · Bear 70(25%) 종목:

| 빌드 | f | 결과 |
|---|---|---|
| 새(3-시나리오) | **1.6085** | 배분에 포함 |
| 옛(같은 데이터) | **−0.6667** | **음수 켈리로 배분에서 제외** |

종목이 계획에서 통째로 사라지는데 경고가 없다. 되돌리려면 순서가 있다:

1. 폰에서 `⬇ 내보내기`로 v5 백업을 받아둔다 (나중에 다시 켤 때 필요하다)
2. 코드를 revert 해서 배포한다
3. **v5 이전 백업으로 `⬆ 가져오기`** 하거나, 각 종목의 `prob` 을 옛 의미(승률)로 손으로
   고친다. 안 하면 종목들이 배분에서 사라진 채로 남는다

계산 수준의 롤백(코드는 새 빌드, 값만 옛 공식으로)은 `kelly3` 에 `p_base=0, r_base=0` 을
넘기면 정확히 같은 값이 나온다 — 축퇴 성질이 그 경로를 겸한다(PRD §7-D20).

**교훈**(§7-D21): 필드를 **추가**하는 것과 기존 필드의 **의미**를 바꾸는 것은 다르다.
후자는 스냅샷 버전만으로 방어되지 않는다 — 옛 빌드는 버전을 보고 거부하지 않고 그냥 읽는다.
